# Systems review architecture · 0.6.1

Kernel Lens is a static execution-performance reviewer. It identifies structures, predicts potential consequences and points to the next investigation. It does not execute user code or establish the fastest implementation.

```text
Source + bounded context + optional imported facts
                    ↓
Lezer syntax trees → CUDA / Python framework adapters
                    ↓
Systems IR (operations, memory spaces, local definitions, control ancestry)
                    ↓
Kernel / graph / distributed / serving lenses
                    ↓
Direct observations + bounded Jev assessments of conditional risks
                    ↓
Evidence gate → JevFinding → editor / sidebar / optional review
```

## Responsibilities

`src/core/systems/types.ts` owns the universal finding contract. Findings carry assessment, structural confidence, exact source evidence, impacts, one next check, requirements and a runtime measurement flag. Additional fields record provenance, evidence level, assumptions and model distributions.

`source.ts` reconstructs visible numbered source and preserves original locations. Missing lines within the current unit, parse errors and truncation prohibit absence-based positive findings. Gaps between imports and a fully supplied function do not invalidate that function. Literal dead branches are suppressed. Nested function bodies do not inherit execution loops around their declaration.

`cuda.ts` maps controls, reductions, barriers, array declarations and accesses. Parameter pointers, shared arrays and local arrays are distinguished conservatively. Shadowed names and unknown calls prevent particular memory claims. It does not implement general pointer alias analysis.

`python.ts` resolves explicit imports and aliases, recognized calls, annotations, local tensor provenance and literal keyword configuration. Reassignment, parameter shadowing and visible API monkey-patching invalidate mappings. Unrecognized callees are retained as coverage gaps. `semantics.ts` is the API behavior table and lens dimension vocabulary.

`lenses.ts` operates on IR. Producer-consumer connections use the nearest visible definition in the same control region; they are not established merely because names appear somewhere in the same function. Static estimates retain their formulas. A ring traffic estimate explicitly names its assumed algorithm and is never converted into communication time.

`review.ts` evaluates up to 24 fixed dimensions against locally extracted source anchors, whether or not a deterministic issue detector matched. `evaluate.ts` combines those questions with at most 12 contextual hypotheses in one request, with no separate routing or source-location request. Direct serial-tail observations, positive structures and supplied metadata do not require a model verdict. Explanations and next checks are authored lens text populated from established facts, not prose generated by Jev.

The compatible legacy assessment envelope remains available for existing review/handoff consumers. The live renderer uses `JevFinding`. The old rubric evaluator remains in source for historical tests and `npm run eval:legacy`; it is not the live performance engine.

## Evidence and probability

High structural confidence means a direct source/API/configuration relationship has been identified. Medium means a qualified inference. Low-confidence findings are suppressed. This confidence does not claim that a performance consequence has been measured.

For direct hypotheses, Jev returns `retain`, `likely`, `dismiss` or `unknown`. For broad dimensions it chooses `issue_E<n>`, `good_E<n>`, `unknown` or `not_applicable`, from at most four pre-extracted evidence anchors. An outcome needs at least the configured aggregate probability (default .75) and .2 probability at its selected location. These inferred findings have medium confidence and never become likely issues. Repeated global output update claims additionally require proven global-address RMW dataflow. The application sums `retain + likely` when deciding whether Jev supports a concern: uncertainty between two issue strengths is different from uncertainty about whether to raise an issue at all. The original distribution is retained for inspection. A strong dismissal suppresses the contextual concern. An insufficient concern probability leaves it unknown.

An inferred or shape/hardware-dependent candidate cannot become `likely_issue` merely because Jev returns a high probability. A strong model outcome cannot fabricate evidence, source locations, quantities or runtime provenance. The evidence gate validates IDs, exact source text and location, nonempty checks/requirements, provenance and finite quantities. This is a bounded evidence contract, not formal verification of arbitrary programs.

## Evidence levels

| Level | Current implementation |
|---|---|
| 0 | Source constructs, known API semantics, local dataflow and explicit policy. |
| 1 | Tensor bytes, equal-sized collective payloads, theoretical ring traffic, explicit conventional KV sizing and supplied launch-width refinement. |
| 2 | Supplied compiler resource/spill reports. No inferred register count or numerical occupancy. |
| 3 | Assumed B200/H100/A100 published ceilings, or imported hardware. Ideal FP32 GEMM intensity and roofline classification for explicit compatible GPU shapes. No automatic topology reconstruction or runtime prediction. |
| 4 | Supplied runtime quantities in their own evidence finding. Other findings stay unmeasured. |

Use **Kernel Lens: Attach Performance Evidence (JSON)** with a complete active block. Imported facts are bound to that source-context revision, are held only in the extension session and expire after a context change. The extension does not run a compiler, profiler or benchmark to acquire them.

```json
{
  "tensors": { "x": { "shape": [128, 256], "dtype_bytes": 2, "device": "gpu" } },
  "launch": { "block": [256, 1, 1], "grid": [128, 1, 1] },
  "compiler": { "registers_per_thread": 64, "spill_loads": 0, "spill_stores": 0 },
  "hardware": { "name": "Your target GPU", "memory_capacity_bytes": 17179869184 },
  "runtime": { "latency_ms": 0.12 }
}
```

Every section is optional. Use measurements from the workload being investigated, not example numbers. Compiler memory quantities, including spill loads/stores, are expressed in bytes. Runtime bandwidth is bytes/second and throughput is items/second. Import validation rejects unknown fields, nonfinite values and invalid dimensions. Supplying compiler or hardware data does not mark latency as measured.

## Deliberate boundaries

This release provides initial adapters, not complete coverage of any framework. Dynamic dispatch, arbitrary wrappers, remote helpers, full alias analysis, distributed launch reconstruction and scheduler internals remain outside the static model. CUDA occupancy, cache behavior, register allocation and compiler transformations require external evidence. An omitted finding is not a good rating.

The model request limit bounds cloud work; the context budget and cached reports bound repeated editor work. Astra remains optional and is restricted to explaining the supplied findings. No generated review or compilation runs automatically in the default configuration.
